[PAGE:1] ABSTRACT
[PAGE:1] This project presents the design, implementation, and verification of a two-level cache controller (L1 and L2) using Verilog HDL. The cache controller interfaces with a CPU-like testbench through address, data, and mode signals, and produces output_data, hit1, hit2, and Wait signals to represent read responses, cache hits, and stall behavior. The system is built as a blocking cache controller, meaning the CPU is stalled during servicing of a request using the Wait signal. To ensure correct transaction handling even when the CPU changes the address or mode signals mid-execution, the controller internally latches each request using stored_address, stored_data, and stored_mode. The controller first checks L1 cache for faster access, then checks L2 cache on an L1 miss, and finally accesses main memory on a complete cache miss. The design is verified using Vivado simulation waveforms, where correct hit/miss behavior, stall timing, and read/write correctness are observed. This project demonstrates the importance of cache hierarchy in reducing average memory access latency and highlights synchronous design behavior through waveform-based validation.
[PAGE:1] CHAPTER 1: INTRODUCTION
[PAGE:1] Overview of the Problem Statement
[PAGE:1] In modern computing systems, processor speed has increased significantly compared to main memory access speed. This difference creates a performance bottleneck commonly referred to as the memory wall. Even if the CPU can execute instructions rapidly, it must frequently access memory for fetching data and instructions, and waiting for memory can drastically reduce overall system performance. Cache memory is used to bridge this gap by storing frequently accessed or recently used data in faster memory close to the CPU.
[PAGE:1] A single cache level may not provide a sufficiently high hit rate for all workloads, especially when memory access patterns vary. Therefore, multi-level cache hierarchies are commonly used, where L1 cache provides the fastest access and L2 cache provides a larger storage capacity to improve hit probability. This project implements a two-level cache controller that supports read and write operations and correctly routes requests to L1, L2, or main memory depending on hit/miss conditions.
[PAGE:1] Significance
[PAGE:1] The design of a cache controller is a key topic in computer architecture because it directly impacts system speed and correctness. A cache controller must maintain correct data flow and must not return incorrect values due to timing mismatches. In synchronous digital systems, signals such as address and data may not always align in the same cycle because data is updated on clock edges, and internal logic may introduce additional delays.
[PAGE:1] This project focuses on building a working cache controller and validating it using simulation. The Vivado waveform analysis provides clarity on how the controller latches requests, generates stall signals, and produces output values only after completing the cache/memory access. Understanding this timing behavior is essential for building correct hardware systems and for interpreting real processor-cache interactions.

[PAGE:1] CHAPTER 2: SOLUTION DESIGN
[PAGE:1] System Architecture
[PAGE:1] The complete system is divided into four major modules: CACHE_CONTROLLER, L1_CACHE_MEMORY, L2_CACHE_MEMORY, and MAIN_MEMORY. The CPU communicates only with the cache controller using address, data, and mode signals. The cache controller acts as the central decision-making unit that determines whether the requested address is present in cache and where to fetch the data from.
[PAGE:1] L1 cache is designed to represent the fastest level of cache with smaller storage. L2 cache is a secondary cache with larger capacity and slightly higher access latency. Main memory represents the slowest storage but contains the complete backing data. The controller follows a hierarchical lookup order: it checks L1 first, then L2, and then main memory.
[PAGE:1] In order to handle synchronous timing correctly, the controller captures each incoming request into stored registers. This prevents issues when the CPU changes its input lines while the controller is still servicing the previous request. The Wait signal is used as a stall mechanism, ensuring that the CPU does not assume the transaction has completed until Wait becomes low.
[PAGE:1] Cache Access Policy (as implemented)
[PAGE:1] Read operation: When mode is set to 0, the request is treated as a read. The controller first checks the L1 cache for the requested address. If the address is found, hit1 becomes 1 and the corresponding data is returned. If the address is not present in L1, the controller checks the L2 cache. If L2 contains the address, hit2 becomes 1 and the data is returned. If the address is not present in either cache, the controller accesses main memory, fetches the data, and returns it to the CPU. After completion, output_data is updated and Wait is cleared.
[PAGE:1] Write operation: When mode is set to 1, the request is treated as a write. The controller latches the address and write-data and begins servicing the request. If the address is present in the L1 cache, the controller updates the L1 cache data for that address. If the address is not present in L1, it searches L2. If found in L2, the controller updates the L2 cache data. If the address is not present in both cache levels, the controller updates main memory directly. This creates a hybrid write behavior where the write destination depends on which level hits.
[PAGE:1] Key Signals and Timing Interpretation
[PAGE:1] The address, data, and mode signals form the external CPU interface. The controller stores the active transaction in stored_address, stored_data, and stored_mode. These stored values represent the current request being processed. The Wait signal indicates the busy state of the controller. When Wait is high, the controller is still processing the request, and the CPU must stall. When Wait becomes low, the transaction is complete and output_data can be considered valid for a read request.
[PAGE:1] The hit1 signal indicates an L1 hit and hit2 indicates an L2 hit. These signals are useful for confirming cache hierarchy operation in the waveform. The output_data signal represents the read result and is updated only after the controller completes the access. Between transactions, output_data remains stable and may hold the last valid read value, which is expected in synchronous designs.

[PAGE:1] CHAPTER 3: IMPLEMENTATION DETAILS
[PAGE:1] Module Responsibilities
[PAGE:1] CACHE_CONTROLLER.v is responsible for accepting CPU inputs, storing the request in internal registers, generating the Wait signal, performing hierarchical lookup, and producing hit1, hit2, and output_data. It coordinates with L1, L2, and main memory modules and ensures correct sequencing of operations.
[PAGE:1] L1_CACHE_MEMORY.v contains the first-level cache storage and maintains valid bits and tag information for each cache line. It supports checking whether an address is present and provides the corresponding data when hit occurs.
[PAGE:1] L2_CACHE_MEMORY.v provides the second-level cache storage with similar tag and valid handling. It is accessed only when L1 misses, and it improves the overall hit rate by storing more blocks.
[PAGE:1] MAIN_MEMORY.v stores the backing memory contents. It is accessed only when both cache levels miss. It provides the correct data for any address and acts as the final source of truth in the memory hierarchy.

[PAGE:1] Transaction Flow (Waveform-Based Interpretation)
[PAGE:1] A transaction begins when the CPU places a valid address and mode on the bus. The controller captures these values into stored_address and stored_mode. For write operations, stored_data is also captured. Once captured, the controller asserts Wait to indicate that it is busy servicing the request.
[PAGE:1] During a read transaction, the controller checks L1 first. If hit1 becomes 1, the data is taken from L1 and later reflected on output_data. If L1 misses, the controller checks L2 and may assert hit2 if the address is found. If both caches miss, the controller accesses main memory and returns the fetched data. The controller updates output_data only when the access is complete and deasserts Wait.
[PAGE:1] During a write transaction, the controller updates the data in the appropriate memory level based on hit detection. output_data typically does not change during writes because it represents read results. The controller clears Wait only after the write operation is completed. This transaction-based model ensures correct behavior and is clearly observable in the Vivado waveforms.
[PAGE:1] CHAPTER 4: RESULTS AND DISCUSSION
[PAGE:1] Simulation Outcomes and Validation
[PAGE:1] Vivado simulation results confirm correct functionality of the two-level cache controller. The waveform shows that stored_address changes only when the controller accepts a new request, proving that the controller latches requests properly. The Wait signal remains high during the servicing period and becomes low only when the request is completed, confirming the blocking interface behavior.
[PAGE:1] The hit1 and hit2 signals correctly indicate cache hits. When the requested address is present in L1, hit1 becomes high and the response is obtained with smaller delay. When the requested address is not in L1 but is present in L2, hit2 becomes high and the controller returns the data after additional delay. When both hit signals remain low, the controller accesses main memory and the output is produced after the largest delay.
[PAGE:1] The output_data signal does not immediately follow changes in the address bus. Instead, it updates only when the controller completes the access and clears Wait. This behavior matches the expected synchronous transaction model and validates correct controller timing.
[PAGE:1] Explanation of Observed Delays
[PAGE:1] In the simulation waveforms, there are visible delays between the time the CPU sets the address and the time output_data updates. These delays are expected because the controller first latches the request internally and then performs sequential lookup across cache levels. Additionally, cache and memory modules update their outputs on clock edges, introducing cycle-based latency even when a cache hit occurs.
[PAGE:1] Another important observation is that the CPU address line may change while the controller is still busy servicing a previous request. In such cases, the controller continues servicing the stored_address rather than the new address, which is correct behavior. This is why output_data may appear to correspond to an earlier address rather than the currently visible address on the bus. The Wait signal helps interpret this correctly by indicating the transaction boundary.
[PAGE:1] Overall, these waveform delays confirm correct synchronous operation and show that the controller is functioning as a blocking cache controller rather than a purely combinational memory interface.
[PAGE:1] Alternate Algorithms Considered and Justification for the Chosen Approach
[PAGE:1] While designing the cache controller, multiple cache handling strategies and algorithms were considered. Each approach differs in complexity, hardware overhead, and performance. The following alternatives were evaluated:
[PAGE:1] Single-Level Cache (Only L1 Cache)
[PAGE:1] A single cache level would reduce design complexity and require fewer resources. However, it provides a lower overall hit rate because of limited storage capacity. For workloads with larger working sets, frequent misses would cause repeated main memory accesses, increasing the average access time. Therefore, a single-level cache was not chosen.
[PAGE:1] Direct Main Memory Access (No Cache)
[PAGE:1] In this approach, every read or write directly accesses main memory. Although it is the simplest to implement, it leads to the highest latency and does not reflect realistic processor memory systems. This option was rejected since the goal of the project was to demonstrate cache hierarchy advantages.
[PAGE:1] Write-Through Policy
[PAGE:1] A pure write-through cache writes data into cache and main memory simultaneously during every write. This provides strong consistency and simplifies correctness.
[PAGE:1] However, it increases the number of memory writes and reduces performance due to frequent memory traffic. It also requires additional control logic for simultaneous updates.
[PAGE:1] Write-Back Policy
[PAGE:1] A pure write-back cache updates only the cache during write operations and writes to main memory only when a cache block is evicted. This improves performance but requires additional structures such as dirty bits, eviction logic, and replacement policies. Since the project focus was on waveform validation and basic hierarchy behavior, full write-back support was considered more complex for the current scope.
[PAGE:1] Non-Blocking Cache Controller
[PAGE:1] A non-blocking controller allows the CPU to continue executing even when a cache miss is being serviced, by supporting multiple outstanding memory requests. This requires request queues, miss status handling registers (MSHRs), and more complex arbitration logic. For a first-level project implementation, this was considered too advanced and difficult to verify within limited time.
[PAGE:1] Chosen Approach and Reason
[PAGE:1] The final chosen design is a two-level cache hierarchy (L1 and L2) with a blocking controller using the Wait signal. This approach was selected because it provides a clear and structured method to demonstrate cache hits, cache misses, and memory fallback behavior. The use of stored_address and stored_data ensures correct transaction processing in a synchronous environment. The blocking interface also simplifies debugging and makes waveform interpretation straightforward. This design gives a good balance between realism (multi-level cache behavior) and implementation feasibility for the given project requirements.
[PAGE:1] Discussion of Potential Improvements
[PAGE:1] Although the current cache controller implementation is functionally correct and verified through simulation, there are several improvements that can enhance performance, scalability, and realism:
[PAGE:1] Add Explicit Handshake Signals
[PAGE:1] Currently, the controller relies on the Wait signal to stall the CPU. Introducing a request_valid and ready mechanism can make the CPU-controller interface more robust and prevent idle cycles caused by timing mismatches.
[PAGE:1] Implement Replacement Policies
[PAGE:1] The current cache behavior can be extended by adding replacement strategies such as FIFO or LRU. This will allow support for multiple cache lines per set and improve hit rate for larger access patterns.
[PAGE:1] Add Dirty Bit and Full Write-Back Support
[PAGE:1] To improve write performance, a dirty bit can be introduced. With write-back, the controller would update main memory only during eviction, reducing unnecessary memory traffic.
[PAGE:1] Improve Cache Associativity
[PAGE:1] Currently, the cache structure can be expanded from direct-mapped to set- associative. Higher associativity reduces conflict misses and increases overall cache efficiency.
[PAGE:1] Reduce Latency and Controller Idle Bubbles
[PAGE:1] Waveform observations show that even when address and mode are stable, output may take additional cycles due to controller sequencing. Optimizing the internal state transitions and allowing early acceptance of the next request can reduce these idle delays.
[PAGE:1] Add Performance Measurement Metrics
[PAGE:1] The design can be enhanced by tracking hit rate, miss rate, and average memory access time. This can be displayed using counters and verified using simulation to quantify the cache hierarchy benefits.
[PAGE:1] Support Burst Block Transfers
[PAGE:1] Instead of fetching or updating single bytes, the controller can be upgraded to fetch full cache blocks (burst transfers). This reflects real cache refill behavior and improves spatial locality benefits.

[PAGE:1] Summary of Key Findings
[PAGE:1] A two-level cache controller was successfully implemented using Verilog and verified using Vivado simulation. The design correctly performs hierarchical access from L1 to L2 and then to main memory. It supports both read and write operations and generates correct stall and hit signals. The use of stored_address and stored_data ensures stable transaction processing, and waveform analysis confirms that output_data updates only after the request is completed. This project demonstrates how cache hierarchies reduce memory access delay and highlights the importance of correct synchronous timing in hardware designs.
[PAGE:1] Future Scope
[PAGE:1] Future enhancements can include implementing an explicit handshake mechanism such as request_valid and ready to improve CPU-controller communication and reduce idle cycles. Replacement policies like FIFO or LRU can be introduced to support multiple cache lines and realistic eviction behavior. A dirty bit and full write-back policy can be implemented to improve write performance and maintain memory consistency. The cache design can be extended to set-associative mapping and larger block sizes. Finally, performance evaluation can be improved by measuring hit rate, miss rate, and average memory access time for different workloads.
